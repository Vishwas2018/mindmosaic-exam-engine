Those literals do not prove human authorship or actual gate execution. That older script is not a safe recovery/import procedure and was not executed.

## Can the current factory truthfully import unknown-origin legacy material?

**Not through a supported, semantically correct unknown-origin route.** See [schema-probe.json](schema-probe.json), produced with pure schema/identity calls, without invoking an ingestion runner.

`candidateProvenanceSchema` requires a generator adapter/normalised identity, `generatedAt`, `generatorVersion` and `promptVersion`. The identity provider enum has no unknown value; the CLI requires a resolvable model alias. `--source other --model unknown` does not resolve. `promptHash` is optional: absence of an authenticated generation prompt alone is not an absolute schema prohibition, and no authenticated API envelope is generally mandatory for manual reviews. The problem is the lack of truthful unknown-origin semantics and separation of generation from import.

A hand-constructed `provider: other` identity with arbitrary non-empty strings can pass the broad identity shape, but it is not the supported CLI route and is not a compliant workaround. Current independence functions compare identity/provider values; inventing an “other/unknown” author could incorrectly make a known reviewer appear independent. Neither a human importer, a Git co-author, a later editor nor a reviewer may be substituted for the unknown original generator.

## Proposed compliant provenance migration — not implemented

1. Add a versioned `legacy_import` provenance variant that explicitly separates **original generation** from **repository import**. Original generation must support `status: unverified` with null provider/model/prompt/hash/time/event, plus scoped evidence references and limitations. Do not insert a fabricated normalised identity or a fake prompt-version string into authoring fields.
2. Record the real import event separately: `importedAt`, actual importer/tool version and operator identity where genuinely known, source Git commit/path/blob, full packet SHA-256, exact raw/candidate/publication hashes, advisory-manifest binding, actual blueprint binding and any explicitly hashed solver-sidecar transformation. An import version belongs to import metadata. It does not become the original prompt version. Preserve all historical records unchanged.
3. Keep existing verified provenance variants and their gate behaviour intact. Unknown-origin status must explicitly fail closed for any independence claim that needs a known generator; absence must never default to human, another provider or “independent”. Propagate the variant through structural validation, review-prompt/ingest, evidence/gate-chain verification, staging and publication. Add refusal tests before permitting real imports. This investigation changes none of these components.
4. After that migration is reviewed and permitted, use a dedicated legacy-import command with a no-write preflight against the exact 12 source bindings. It may create genuine import records only; it must not fabricate historical generation or review events, infer revision numbers from authoring notes, auto-stage or publish. Retain existing manual reviews as advisory attachments with their actual provenance.
5. Run the real registered gates against the resulting actual revisions. Generate fresh bound review prompts where needed and ingest complete genuine responses. While original generator identity remains unknown, the existing different-provider rule cannot be asserted satisfied. Recover stronger evidence or obtain an explicitly reviewed governance-policy decision for unknown-origin material before claiming that gate can pass. A policy decision cannot retroactively establish a provider/model or manufacture review history.
6. Only after legitimate staging, generate the final human approval sheet. Formal owner sign-off, merge, publication and production release remain separate and unauthorised. Re-authoring through a verifiable process, if ever chosen, would produce a new revision needing new review; it must not silently replace these 12 accepted revisions.

## Reproduction and verification

`npx tsx scripts/scholarship-source-register.mts` reconstructs the Git register and pure identity/schema probe, validates all 12 unchanged candidate/publication hash pairs and writes only this documentation directory. Optional `--historical-inventory <local-inventory.json>` reads the listed historical records and adds actual candidate/publication comparisons; it creates no factory repository or records. The local execution index contains fixed record/file hashes for independent local inspection; the raw logs remain outside Git.

No application or governance implementation is changed. Relevant verification consists of this read-only reconstruction, hash/coverage checks, TypeScript and lint for the added audit tool. Previously completed application, RLS and browser tests are not manually repeated for this documentation investigation.

Actual results: reconstruction passed for all 12 manifest-bound revisions; all 36 inventoried historical file hashes remained unchanged when re-read for comparison; `npm run typecheck` passed; `npx eslint scripts/scholarship-source-register.mts` passed; `git diff --check` passed. Git comparison with the investigation baseline shows no question, runtime, historical review/manifest, factory lifecycle or approval changes. The only executable addition is the read-only documentation audit tool.
